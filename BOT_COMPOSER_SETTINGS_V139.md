# Bot composer settings and bottom bar, v139 follow-up

Base: `8538e9689da0f3aede0469f8860b620231e3aa42` on `codex/bots`. Isolated branch: `codex/bot-typing-recent-3d829950`. The live `/bots` route redirected an unauthenticated request to sign-in; no user bot or conversation was opened. Local Chromium rendered the actual workspace and CSS against synthetic bots.

## Cause and implementation

- **Confirmed in source:** Plan and Fast previously read the last bot snapshot while shared asynchronous `action()` left the controls enabled. Rapid taps could send repeated stale values. Fast compared only the first catalog tier, missing a valid effective `priority` or `fast` tier. Errors appeared in the distant header. The extracted `ComposerSettings` serializes one change per bot, shows a tentative pending state, uses the saved bot response for immediate confirmation, and shows errors beside the controls. An uncertain acknowledgement blocks a new setting operation until Check setting or an explicit retry with the same operation ID; definite rejection restores the prior state.
- **Native queue correction after independent review:** v2 `ThreadSettingsUpdateParams` documents model, effort, tier and collaboration mode overrides **for subsequent turns**. Native queue advance can start the next turn without `startQueued`, so skipping `thread/settings/update` during an active turn was wrong. `runtime.update()` now awaits native settings acknowledgement before saving the new bot choice, active or idle. A current turn retains its already selected settings. New turns that start *after the native update* inherit the choice, whether started by `turn/start`, bridge queue dispatch, or native automatic queue advance. While awaiting native acknowledgement, a turn notification can advance `activeTurnId`; the final bot save applies only setting fields to the latest stored bot, preserving that new turn. A definite native rejection leaves the stored preference unchanged and surfaces an error. A lost acknowledgement remains uncertain rather than prompting a blind replay.
- **Snapshot correction after independent review:** Every bridge `saveBot` emits a sequenced bot event, and `snapshot.cursor` is the event sequence. `BotsClient.refresh()` no longer applies or returns a response older than its current cursor; older replay events cannot roll the snapshot back. Responses from an earlier owner epoch are rejected even if the same owner ID returns after a switch. `ComposerSettings` retains an accepted local setting until a snapshot newer than the request's starting cursor confirms the same values. Reconnect and background refreshes therefore cannot briefly restore the old Plan/Fast state after a successful reply.
- **UI:** The aligned bottom row groups model/effort with distinct Plan/Fast pressed states and a stable pending indicator. “Future turns” on desktop and “New turns after saving · This run keeps its settings” on mobile describe the native boundary precisely. Attachment, queue, send, stop, composer input and durable draft code are unchanged.

## Focused evidence and limits

Direct runtime calculation with a temporary synthetic SQLite store and Codex stub: an active Plan + standard-tier change made **one** native `thread/settings/update` call before persistence, carrying `mode=plan` and `serviceTier=default`. The stub held its acknowledgement while a native-auto-next turn ID was saved; after acknowledgement the bot retained that newer ID and the chosen settings. This proves call order and bridge state merging, not timing inside a production Codex process. The generated protocol explicitly scopes settings to subsequent turns. If an automatic turn starts *before* native acknowledgement, that turn may retain the prior settings; the UI says turns started after saving, and no claim is made that an in-flight update retroactively changes it.

Direct client calculation: an event at cursor **11** kept Plan when a delayed snapshot at **10** returned; a snapshot at **13** stayed authoritative when a delayed **12** returned. An earlier owner epoch's response was rejected. A matching settings event has a cursor greater than the request baseline, so the accepted local value can then be released. No automated test suite was added or run.

Local Chromium workspace inspection with synthetic transport: two rapid taps during pending Fast yielded **one** `bots.update`, with both controls disabled until acknowledgement. A rejection restored the prior Plan state and showed its error beside the controls. An uncertain result left the setting locked; Check made no mutation and Try again reused the same operation ID.
