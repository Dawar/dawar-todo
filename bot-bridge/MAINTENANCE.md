# DawarTodo deployment and recovery

Routine task approval covers implementation, scoped corrections, compatible deployment and recovery through the working installed result. Do not require another approval for each preparation, pre-effect correction or compatible activation. A new owner decision is needed only for unrelated access expansion, destructive data changes, external business actions or a missing owner choice. There are no quiet hours or time-of-day admission restrictions. Source-ready and installed remain separate.

## One deployment command

Run outside a native bot turn:

```sh
node portable/deploy-cli.mjs --plan /absolute/private/deployment.json
```

Use Node24 on Linux. The owner-reviewed private plan binds the original operation, old source/PID/start/invocation, exact target release manifest/native binary, expected model catalog, service/controller unit identities, SQLite/configuration files and original writer/placement identity. No credentials appear on argv or in receipts. The controller reads the existing maintenance credential only inside the exact old process boundary.

The transaction records prepared → draining → backup verified → stop intent → old process exited → start intent → healthy → finalized. Every stop/start has an intent before its effect. Re-running the SAME unchanged plan reconciles actual process state; an uncertain stop/start is never issued again. Changed payloads conflict. Controller ownership is transactional, with process identities and retained history. Legacy failed claims/leases are not inputs to this workflow.

## Admission and backup

Drain at most15minutes. Native/user work, active native Goals, accepted queues, tools, external writers, volatile secure inputs and unknown current effects must settle. Fresh process-owned loaded-thread/Goal/queue/background-terminal reads prove native idle. Registered retained inputs/nonblocking completed notices require their ORIGINAL identities and fresh terminal projection evidence. Unrelated account history is not liveness.

The hub and native fences are acquired before consistent private SQLite backups. Config files are backed up separately with exact hashes. A claimed original fence can be released before shutdown starts using owner-only `release-before-stop`, with a fresh idle proof; ordinary cancelled/expired leases cannot reopen. Original claim time and failure receipts remain retained. After any lifecycle effect, reconcile the original transaction instead of releasing a fence or creating an alternate helper.

## Retained records and shutdown

Owner-reviewed `retainedRecordsPath` binds byte-exact orphan lifetime records and separately retained native/provider/pre-effect evidence. The SAME contract is used by hub drain and voice observation/shutdown. It records ended lifetimes; it does not settle uncertain effects, delete records, replay calls or enable old alarms. Missing/changed evidence remains a blocker. Live asynchronous work and voice sockets/requests always block.

After fresh claimed proof, close the gateway, native stdio and idle desktop MCP transports. Await actual child exit with a bound and no signal escalation. Preserve XFCE/browser sessions and unfinished pages. Do not kill active work or tools. The controller issues one graceful service stop; a pending job or refusal is an explicit reconciliation state, never permission to force or retry it.

## Public service and recovery

Reconnect sync separately requests bounded original journal receipts for native-accepted/running/unknown operations behind the command cursor. This is negotiated by `durableReceiptRecovery`; older nodes retain their existing protocol. Recovery sends receipts, never old inputs or native turns. Original fingerprint, owner, node, bot, placement epoch and synchronized control must match. The rotating receipt cursor prevents an unresolved old operation from starving later receipt recovery. Deployment transactions retain their latest actual idle observation so a timeout reports current work or a concrete uncertainty rather than an unexplained gate.

The persistent public front and existing Cloudflare connector are separate from native execution. The front proxies authentication/data through the one authoritative gateway. Only fixed public assets can fall back to the standalone site. Before origin connection, refusal is definite; after a lost origin response, delivery remains uncertain with its original ID. Website sessions, native Codex sign-in and external thread ownership have different recovery actions. Close the other native client normally; never remove its lock. Effective client permissions are Unknown unless actually observed.

## Rollback

Rollback changes reviewed code/configuration after proving current writer ownership and idle. Use a NEW explicit rollback transaction linked to the original healthy deployment and current process, retaining all receipts, epoch/placement claims and post-cutover input. Never restore an earlier SQLite backup over newer data. An old backup is an isolated recovery artifact, not a routine rollback command.

The detailed old contracts, historical one-use attempts and evidence remain in [maintenance-history-20261012.md](maintenance-history-20261012.md) and their original private receipt directories. They are history, not additional current approval gates.

## First installation from an older guard

An explicit `compatibilityBootstrap` in the private deployment plan consumes the owner's standing recovery amendment. It verifies the original native human record, installed process/binary identity, current RAM counters, registered native turn/Goal/queue metadata, terminal inputs and byte-exact pre-effect refusals. It uses the same installed admission hold and hub freeze, and records `installedSealClaim: false`; it never fabricates a native claim or resets an older attempt.

After the consistent private backup and original stop intent, the controller may close the proved-idle native stdio child and registered idle desktop transports. Each signal has a durable original intent. Only after every descendant has exited and the old cgroup contains solely the idle parent may it terminate that legacy parent to finish the pending stop. Active native work, tools and GUI/browser sessions are never killed. The next installed runtime uses its normal shared retention/shutdown contract, so this compatibility path is not a recurring deployment prerequisite.
