# Owner blast Edit contract

Original approved work: `cody-unified-blast-edit-20261013-v1`. Additive capability: `burstEdit: 1`. This is logical input checkout, never a native send, turn interruption, Goal action, or queue transfer.

`bursts.checkout` takes the exact registered `threadId`, current `controlRevision`, an opaque durable browser `destinationId`, and the complete current eligible batch IDs/revisions. The authenticated owner browser supplies one original operation ID. Native reservations, portable mailbox rows, Plan dispatch fences, different threads, superseded batches and changed revisions are rejected. Validation and reservation run synchronously in the existing local acceptance transaction, before any countdown/native preparation can consume these sources.

A positive `checkout` receipt retains the original operation/bot/params, ordered original message IDs/text/replies and registered attachment IDs/metadata. Sources become `editing`; neither the local nor canonical hub scheduler admits that state. The source records and original receipt remain durable. Receipt recovery must use the same operation and parameters, not a new destination or replacement input. `bursts.checkoutRead` returns this exact original receipt to its owner and original thread/browser destination.

The complete receipt is limited to 1 MiB minus 4 KiB for the existing protocol envelope. If the receipt or registered files cannot be supplied safely, a positive `blocked` receipt identifies the exact operation/params and a fixed bounded reason. The captured sources become paused and remain saved; the browser does not copy, consume or submit them. Deliberate Send now remains separate. `burst.edit` is a bounded metadata-only invalidation carrying the original thread/operation, using the existing durable event sequence. Its consumer refreshes the bounded current source and rejects pre-invalidation/foreign responses.

The browser first journals its original Edit identity in the ordinary critical draft IDB. It persists the positive source receipt and original recoverable drafts before merging. A strict draft transaction prepends the source texts with newline separators, unions files by registered ID while preserving existing local bytes/readiness, and records an idempotent saved marker. Concurrent typing is merged against the latest ordinary draft. Scope/owner/thread/slot replacement cannot apply a late merge. Multiple quote sources remain explicit in Saved drafts; the current quote is retained. Inputs exceeding the editor's existing text/file/image limits are preserved as separate complete drafts, with a visible explanation and the current editor unchanged.

Only after a positive strict draft commit does `bursts.checkoutCommit` use a separate durable identity derived from the original checkout ID. Its params identify that exact original operation/thread/destination. It marks only those reserved sources `edited`; original records and receipts are retained. Lost acknowledgements retain the saved phase and the original confirmation ID, so recovery cannot prepend twice or send. New messages submitted after reservation form an independent waiting blast. Unavailable browser storage or a different device remains an explicit recovery constraint.

Local routing rejects trusted bot/tool origins before original receipt recovery. Canonical hub routing uses the existing authenticated owner scope and authoritative writer/freeze transaction. The methods are logical hub controls; no new agent command, native RPC, placement/context route or admission rule is added. A hub never inherits an agent's generic Edit capability: it advertises it only with authoritative compatible canonical checkout controls.

The UI shows one pending aggregate and Send now/Edit. Unconfirmed additions remain visibly unconfirmed and cannot be checked out. Sent/native receipt display retains one aggregate, original part anchors and lazy original quote controls. Stored/native transcript text is unchanged. Existing ordinary Queue, Stop, prior Queue/Pause/Discard receipts, quiet-window settings, native canonical identities, drafts, files, replies and reading intent retain their contracts.

Rollout requires the compatible reviewed frontend and logical bridge/hub source. Publication alone is not installation or genuine device/native acceptance. If frontend rollback is necessary, keep checkout support until outstanding `editing`/confirmation receipts are reconciled; never rewrite those records into pending/sent, clear them or replay them to make an older backend appear compatible.
