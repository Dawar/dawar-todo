# Owner task-file export contract, version 1

Jim owns this adapter; Cody owns task-to-queue UI, native queue admission and confirmed delegation. Ordinary source todos/files remain intact. Export readiness alone never hides, completes, deletes or queues a task.

Types: `lib/task-queue-export.ts`. Owner session only, using the existing configured `BOTS_OWNER_USER_ID`/email/origin boundary. API bearer tokens and guest request links cannot export. Existing tasks are the app's single-owner catalog, without per-task account columns; this adapter does not introduce multi-tenant task sharing.

1. `GET /api/todos/{id}/queue-export?botId={registeredBot}` returns `{source,taskQueueExports:1}`. Source contains exact title/notes, updatedAt, opaque SHA revision and ordered confirmed file descriptors. It includes no keys/URLs. Cody must compare saved task state and every confirmed attachment against the current local selection, and block unsaved/pending/offline edits before POST. Do not silently accept the GET's saved content in place of unsaved text.
2. Persist a per-task original export intent and destination before `POST` to the same path with `{operationId,botId,sourceRevision}`. Response is `{receipt:TaskQueueExportReceipt}`. Repeating those exact values returns the same receipt, file IDs and snapshot. A confirmed different task/version/destination is an operation conflict. Unknown outcomes retain/reconcile the original operation, without alternate IDs or legacy upload fallback.
3. The existing private storage endpoint supports POST action `taskQueueExport` with `{taskExportId,botId}`. It uses the existing storage-service credential and machine fence, not the owner endpoint's token. `runtime.storage.resolveTaskExport(bot,taskExportId)` returns `{receipt,sourceCurrent}` after verifying the exact bot/ID/file shape. Server revalidates destination registrations. No new tool, arbitrary-key API or public grants are exposed.
4. Before **new** queue acceptance, require `sourceCurrent === true` and bind the receipt's task ID, revision, original export operation and destination to the saved transfer intent. Build ordinary task message content from the server receipt, not arbitrary browser snapshot text; use exactly its destination attachment IDs. Existing `importAttachment`/`inputFor` materialize verified bytes in the destination uploads directory. This helper does not invoke inference, queue.add or any composer mutation.
5. Cody owns the optional `taskExportId` queue parameter, queue-source/fingerprint/receipt persistence and paired native capability. This contribution deliberately edits no queue runtime/types/state machine. Reconcile an already accepted/consumed original queue receipt **before** checking the current task again; source changes/deletion or a failed later export lookup cannot trigger another queue.add. Preserve source binding through list moves/checkout/bursts/dispatch and allow ordinary explicit queued edits. The original export snapshot stays immutable.
6. Cody's separate confirmed queue-delegation marker must validate owner/task/revision/export/queue operation, bot/list and positive queue or consumed-turn receipt. Source edits race safely: newer tasks stay visible. Preparation, copied files, failed/uncertain outcomes and native dispatch delivery alone are not task completion. No Delete/Complete/archive/recurrence/urgent changes in this adapter.

Limits: at most12 ready originals, each100MiB (existing bot limit), title+notes at most190,000 JS characters to reserve room below the existing200,000 message cap. Larger task videos/text return actionable limit errors; nothing is truncated/omitted. Source file names retain the task limit; destination names use existing bot160-character normalization. Existing immutable originals have no historical SHA column: export establishes SHA by reading the current authenticated original, ETag-fences server copy and verifies the destination SHA/size. This proves the transferred current bytes, not historic uploaded bytes against a nonexistent original checksum.

Codes include `source_not_ready`, `source_changed`, `export_pending`, `conflict`, `limit`, `integrity`, `not_found`, `uncertain`. Changed current source reports false for normal edits; deleted/pending/over-limit current sources can reject resolution. Retain prior accepted receipts rather than replaying work. Concurrent copies use a durable10-minute lease with an overall10-minute provider abort signal; failure releases it, process death requires expiry before same-ID recovery. An uncertain copy is sent once, then its immutable key is verified on retry; the generic replay helper is intentionally bypassed only for this task copy. Confirmed corrupt copies can be repaired from the verified original under the same ID; no valid file is replaced/deleted. Metadata input is16KiB with a60s body deadline. Browser metadata deadline/unknown ACK can precede the server's final receipt; reconciliation stays same-ID.

`0035_task_bot_exports` and matching runtime bootstrap are additive/idempotent, with a scoped unique operation index. No cleanup/eviction policy or access expansion. Deleted-bot metadata is mirrored privately at bridge registration; native admission must also recheck the actual local deleted/archive state to handle catalog lag.

Release through Dwight: additive cloud API/schema first, compatible bridge resolver plus Cody admission/capability next via one strict-idle handoff, then UI adoption. Cloud `taskQueueExports:1` only describes the export API, not a working native queue feature. Keep controls gated until both producers/consumers are accepted. Rollback disables those controls; retain originals, exported registrations and receipts. Older clients remain compatible; never drop the table or replay an uncertain transfer. Real owner transfer, provider and physical device acceptance remain separate from disposable source checks.
