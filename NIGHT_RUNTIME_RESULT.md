## Plan ordering and boundaries

- Every managed main `turn/start` sends explicit `collaborationMode`; normal interactive/staged starts use the freshly settled app intent. Scheduled starts, scheduled notice continuations, ordinary manager notices and manager-worker starts use explicit default. Native `turn/steer` never reconfigures an active turn. `thread/resume` is not an automatic mode reset.
- The checked-in v2 `TurnStartParams` contract documents explicit collaboration mode and its settings precedence. This pass relies on that contract; it did not verify real native execution. App snapshot/bot events expose app-owned future-turn intent, **not proof of a sticky native default reset**. `bots.read` returns stored app settings. External native clients that omit mode are outside this guarantee.
- Successful proposed-plan completion is required. Clarification-only replies, incomplete plan evidence, checklist updates, streaming fragments, failure/interruption, scheduled work and worker/notice turns cannot consume interactive intent. Missing final evidence uses the original bounded native lookup. A newer explicit mode operation stays owned by that operation, including an unconfirmed one; its outcome is never inferred from matching settings. Subsequent managed starts use the last confirmed app mode, not an unacknowledged settings request.
- New queues are bridge-staged, so completion/intent settlement precedes their explicit-mode dispatch. Main-turn/input/pause/uncertainty gates remain; worker activity is not a queue barrier. Legacy native entries keep their prefix, IDs and native automatic behavior. Plan enable/start requires that legacy queue to drain. The bridge cannot retrofit native automatic-dispatch pause semantics or protect against an external client inserting native queue entries.
- If records from the unpublished old reset candidate exist, the original reset ID and unresolved outcome remain under `legacyNativeReset`; consuming app intent is not native receipt resolution. They no longer permanently block all managed starts/settings. Legacy inherited-mode queue fallback stays gated for an unconfirmed old reset. Existing pauses are not silently removed: explicit `queue.resume` is available after local gates settle. No legacy record was deleted or tested on live storage.

## Queue/UI integration contract for f48ec478

Minimal typed additions are in `lib/bots-operations.ts` and `lib/bots-types.ts`; frontend/history/projection/preferences files are untouched. Preserve the conversation worker's separate optional `BotQueuedSubmission` fields when integrating these type additions.

- `queue.update({id,text,attachments?,expectedRevision?})` and `queue.delete({id,expectedRevision?})`: revision is an optional positive safe integer for staged rows only, compared **inside the mutation transaction**. Invalid/mismatched revision or noneditable state returns `outcome: rejected`, with no queue effect. Omission preserves old clients. Supplying a revision for a legacy/native or absent item rejects. Send the revision only when creating a new action; never add it to a previously persisted exact-ID request because that changes its fingerprint.
- `queue.reorder({ids})`: every listed ID exactly once; any staged dispatching/uncertain item rejects. Mixed reorder preserves the complete legacy prefix and changes only the staged suffix. Server enforcement does not rely on disabled UI controls.
- Local add/update/delete/reorder/resume use atomic `localOnly: queue-v1` receipts. Read/validation/rollback failure before any queue effect is definitely rejected. If commit or its outcome cannot be established, uncertainty is retained; a visible done receipt returns success even if publication failed. `queue.resume` commits its receipt before scheduling the next tick. It does not itself issue a native start.
- Legacy native update/delete/reorder retain native paths. Delete/reorder now track the effect boundary: local validation before the call can reject, but **any error after those native calls begins remains uncertain**, including explicit RPC errors without a reviewed no-effect receipt. Local errors after a successful native call are also uncertain. Existing send/update native rejection semantics are unchanged. Old untagged/ambiguous receipts are never replayed because a row/history page is absent. No `queue.list` equality is used to settle delete/reorder/resume.
- Error envelopes remain compatible with the deployed old relay and plain-string old clients. No relay publication is required for these additions.

## Continuation discovery contract

`runs.turns`, with request `botId`, accepts `{runId, cursor?: string|null, limit?: number}` and returns `{turns: BotRunTurn[], nextCursor: string|null}`. Default limit 25; integer range 1–50. The parent run is validated for the authenticated bridge owner's bot. Cursor schema/version, bot/run identity and a 2048-character size cap are checked; SQL is bot/run filtered, indexed and limited to `limit+1` rows. No native history request or file read occurs.

Each receipt is metadata only: `{id,botId,runId,operationId,turnId:string|null,status,error:string|null,createdAt:string|null,finishedAt:string|null}`. Error is bounded to 2048 characters; missing/invalid dates stay null. `id` is the continuation's original operation ID. Pagination is deterministic ascending identity order, not completion-time order; mutable status/date changes cannot move a receipt between pages. New entries before the current key require page-one refresh. The primary turn remains solely on `run.turnId` and is not repeated in this list. Existing bot-scoped `history.turn`/history detail routes can read discovered turn IDs on the same `main-legacy` thread.

Snapshot adds optional `activeScheduledTurns: Array<{botId,runId,turnId,operationId,continuation:boolean}>`. Bot-scoped `schedules` events add `activeScheduledTurn` (object or null). Continuation state events additionally include `runTurn` (the metadata above; primary-only updates use null). Missing fields mean old service; null active attribution means no currently attributed scheduled main turn. Terminal receipts/evidence cannot be advertised as active. Existing event sequence/replay envelopes are unchanged.
